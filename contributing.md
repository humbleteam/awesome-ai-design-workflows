# Contributing

Thanks for adding to the list. The bar is simple: would a design team be better off knowing about this?

## Adding an entry

1. One entry per pull request.
2. Format: `- [Name](https://example.com) - What it does.` Sentence case, ends with a period, no marketing adjectives.
3. Describe what the thing does, not what it promises. "Predicts attention from an eye-tracking-trained model" is an entry. "Revolutionizes UX research" is not.
4. Put it in the section it belongs to, alphabetically only where the section is already alphabetical. Most sections are ordered by usefulness, so say in the PR why yours sits where it does.
5. Check the link resolves. Dead and redirect-chained links are the main way a list like this rots.
6. Say in the PR description whether you are affiliated with the entry. Affiliation is not a blocker, an undisclosed one is.

## What gets declined

- Waitlists, closed betas, and anything without a working product behind the page.
- Paid courses, lead-magnet PDFs, and gated content.
- Tools whose only AI claim is a chat box bolted onto an unrelated product.
- Link shorteners and referral or affiliate links.
- Blog posts that restate the obvious. Research, benchmarks, and survey data are welcome.

## Removals

Open an issue if an entry is dead, acquired and shut down, or no longer does what the description says. That is as valuable as an addition.

## Checks

Every pull request runs `awesome-lint` for list formatting and a link checker over the README. Both need to pass.
